# Задача B85-12 — маунт корня эпика у delegate не материализуется на хосте

**Статус:** done · **Ветка:** compatible-pi · **База:** 84e0515

## Диагноз

Механика: `--mount h:c[:ro]` собирается в `sandbox.mounts` (pi-companion `executeRun` → `sandboxForRun`),
а в docker-аргументы превращается в `lib/sandbox.mjs` (`buildDockerRunArgs` → `-v resolveMountSource(...)`):
`~` раскрывается, относительный путь резолвится против run root. Путь ВНЕ рабочего каталога
(корень эпика — как раз такой) обрабатывается так же, как любой другой bind-маунт, — и **никто не
проверял, что хостовая сторона существует**.

Docker никогда не отказывает на несуществующем bind-источнике: он молча создаёт пустой каталог — на
файловой системе демона. Там, где демон живёт в своём mount-namespace (rootless, docker-in-контейнере,
удалённый daemon), этот каталог виден только демону: агент пишет отчёт в контейнерный «аналог» пути,
рапортует успех, на хосте — «отчёта нет». Ровно три случая за два эпика.

### Пробы

- **not_executed (живой delegate):** полный `pia delegate` требует ключа модели и тратит токены;
  из песочницы реальный прогон недоступен по условиям задачи («работающий экземпляр не трогай»).
- **Выполнено, docker-уровень:** `docker run -v /tmp/b85-12-nonexistent-host:/data busybox …` — контейнер
  стартует без ошибок, файл в контейнере создан. В ЭТОЙ песочнице путь материализовался (демон делит
  файловую систему с клиентом), что подтверждает: сама механика «создам пустой каталог молча» есть,
  а виден ли он на хосте — зависит от того, где живёт демон. На машинах из бэклога — не виден.
- **Выполнено, минимально (функция трансляции на реальных аргументах):** прямой вызов
  `missingMountSources`/`sandboxPreflight` на маунте несуществующего корня эпика до фикса не было вовсе;
  после фикса — см. «Фикс».

## Фикс (выбран вариант а — fail-fast верификация; вариант б не потребовался)

`lib/sandbox.mjs`:

- Новый экспорт `missingMountSources(sandbox, { homeDir, cwd })`: для каждого маунта с путевой
  хостовой стороной (именованные volume пропускаются) вычисляет хост-путь той же функцией, которой
  docker получает `-v` (общий хелпер `mountHostSide`, извлечён из `resolveMountSource` — проверка судит
  ровно тот путь, который получит контейнер), и возвращает те, которых нет на хосте.
- Проверка встроена в `sandboxPreflight(sandbox, { cwd })` — рядом с проверкой образа и демона, то есть
  ДО создания джоб-рекорда. Ошибка именует маунт, путь, причину («agent would write into a
  container-only analog of the path») и что делать («Create the directory first»).

`pi-companion.mjs`: оба вызова preflight (run-путь и `pia setup`) передают `cwd` (run root / workspace root).

Вариант (б) — автоперенос отчёта после финализации — не реализован осознанно: при fail-fast на старте
джоб в «фейковый» маунт больше не попадает, переносить нечего; перенос по эвристике из ответа агента
имел бы ненулевой риск ложных файлов и сломал бы контракт вывода. Если поверхностный случай останется
(демон, создающий каталог у себя при существующем на клиенте пути — недостижимо клиентской проверкой),
это отдельная задача.

## Тесты

Новая группа `tests/mount-verification.test.mjs` (7 тестов, короткий `--test-timeout=10000`, без сети и
без фетчей):

1. существующий путь вне workspace — не флагуется;
2. несуществующий путь — флагуется с точным hostPath (кейс «корень эпика»);
3. относительный источник судится против run root, не cwd процесса;
4. `~/...` раскрывается до проверки;
5. именованный volume не флагуется;
6. не-песочный запуск — нечего проверять;
7. `sandboxPreflight` отказывает до джоб-рекорда, сообщение содержит путь, причину и слово «analog»
   (регресс-тест B85-12).

Попутно поправлен `tests/preset-pools.test.mjs` (e2e-тест run path): его заглушки сервисов маунтили
несуществующие `/srv/base`, `/srv/extra` — новый префлайт теперь честно их отказывает; заглушки
переведены на временные каталоги с уборкой в `finally`.
